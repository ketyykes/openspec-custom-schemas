    Process every unchecked checkbox in tasks.md in order.
    **The review unit is the tasks.md `##` group, not the single task:
    implementation is dispatched per task, but Stage 1 / Stage 2 run once
    per group, at the group boundary. Do not reorder, skip, or merge.
    (REFACTOR-only groups run a reduced flow — see below.)**

    Commit behavior assumes the agent host has git permission. If commits
    cannot be made, the discipline degrades to in-memory steps; do not skip
    the test-first sequencing regardless.

    ─── Per Group: coherence pre-flight ───
    1. Identify the current group: the next `##` section in tasks.md with
       unchecked boxes. Confirm it ends in a spec-coherent state: the
       group's tasks combined leave no dangling intermediate state (e.g.,
       a helper nothing inside the group consumes). If the coherent point
       lies in a later group, stop and fix the grouping in tasks.md (a
       planning fix, not a code fix) before dispatching anything. A group
       should stay within 3 RED/GREEN pairs.
    2. Note the current commit hash as the group's review base; the group
       diff reviewed in Steps 6-11 is everything committed after it.

    ─── Per Task (inside the group): dispatch Implementer ───
    3. Read execution-plan.md for the Implementer's default_model and upgrade triggers.
    4. Dispatch a fresh subagent as Implementer with:
       - The complete text of the task from tasks.md (the RED + GREEN pair)
       - The matching entry from test-plan.md (test name / scenario / assertion / why first)
       - The relevant spec.md section (only the capability this task touches)
       - The relevant design.md section (decisions and constraints affecting this task)
       - If the task produces an intermediate state (something only a later
         task in this group consumes), one line naming that consumer task
         and how it will consume it (so the interface lines up)
       - Explicit instruction: write the RED test → run tests, see it fail
         → write minimum GREEN implementation → run tests, see it pass
         → self-review → commit
    5. Implementer reports status:
       - DONE: dispatch the next task in the group; after the group's last
         task, proceed to Step 6 (Stage 1).
       - DONE_WITH_CONCERNS: read concerns. If they are about correctness or scope,
         resolve before continuing. If they are observational (e.g., "this file grew
         big"), log and continue.
       - NEEDS_CONTEXT: supply the missing context; redispatch with the same model.
       - BLOCKED: follow escalation rules — context gap → add context;
         reasoning gap → upgrade model; task too big → split; plan wrong → escalate.
         Never redispatch the same model under the same conditions.
       Do not check off any box yet — boxes are checked only after the
       group passes Stage 2.

    ─── Per Group: Stage 1 — Spec Compliance Review ───
    6. When every task in the group reports DONE, dispatch a fresh subagent
       as Spec Reviewer (model per execution-plan.md) over the group's
       combined diff (all commits since the review base). It receives the
       group's full task texts, the matching test-plan entries, and the
       relevant spec / design sections.
       Required first action for the reviewer: restate the section headings of
       the spec / test-plan excerpts it received; if they do not match the group
       under review, report NEEDS_CONTEXT instead of reviewing (the orchestrator
       reassembles the context and redispatches).
    7. Sole task: compare the group's code against spec and test-plan; answer
       "does the code match the spec?"
       - Look at: requirement coverage of the capability, scope creep,
         RED → Scenario mapping for each task, and whether every intermediate
         state inside the group got consumed by the group's end.
       - Do NOT look at: naming, structure, quality (that is Stage 2's job).
       - Each finding must name the task number(s) it concerns.
    8. ❌ Stage 1 fails → one fresh Implementer fixes the group's findings
       (dispatched with the findings list and the affected tasks' context)
       → back to Step 6.
       ✅ Stage 1 passes → proceed to Step 9.

    ─── Per Group: Stage 2 — Code Quality Review ───
    9. Dispatch a fresh subagent as Code-Quality Reviewer (model per
       execution-plan.md) over the same group diff.
       Same required first action as Stage 1: restate the received excerpt
       headings; on mismatch with the group, report NEEDS_CONTEXT — reassemble
       the context and redispatch.
    10. Sole task: review implementation quality.
        - Look at: naming, duplication (including between this group's tasks),
          edge cases, error handling, readability, consistency with existing style.
        - Do NOT re-litigate whether the spec is right (Stage 1 already covered that).
        - Each finding must name the task number(s) it concerns.
    11. ❌ Stage 2 fails → one fresh Implementer fixes → back to Step 9.
        ✅ Stage 2 passes → check off every box in the group; proceed to the
        next group (back to Step 1).

    ─── REFACTOR tasks ───
    Dispatch a fresh Implementer per REFACTOR task like any other task in
    its group, with this contract instead: refactor only, no behavior
    change, full test suite stays green, commit `refactor: <description>`.
    At the group boundary its commits are covered by Stage 2; Stage 1
    findings must not target them (no spec-visible behavior may change).
    A group made up solely of REFACTOR tasks skips Stage 1 and runs
    Stage 2 only.

    ─── After all groups complete ───
    12. Dispatch a fresh subagent as Final Code Reviewer (model and checklist
        per execution-plan.md) over the full set of commits to confirm
        cross-group integration is consistent.
    13. ❌ Final review fails → Implementer (fresh subagent) fixes → back to
        Step 12.
        ✅ All green → apply done.

    ─── Forbidden ───
    - Dispatching multiple Implementer subagents in parallel (they will conflict)
    - Reviewing mid-group "for safety" (mid-group states are legitimately
      intermediate; per-task review re-creates the false-positive churn the
      group boundary exists to remove)
    - Skipping Stage 1 or Stage 2 at a group boundary (REFACTOR-only groups
      run Stage 2 only)
    - Starting Stage 2 before Stage 1 failures are resolved
    - Checking off any box before its group passes Stage 2
    - Moving to the next group without running the fix-loop on reviewer findings
    - Letting the Implementer's self-review replace group review (both are required)
    - Waving through "close enough" spec deviations
    - Redispatching a BLOCKED task with the same model under the same conditions
    - Letting any subagent read plan files directly (always paste the full task text)
    - Dispatching into a group that failed the coherence pre-flight
      (fix the grouping first)

    ─── When blocked ───
    - Stop. Record the blocker under `## Open Questions` in design.md.
    - Report back to the user.
    - Do not simplify tests or skip verification to make progress.
