    Process every unchecked checkbox in tasks.md in order.
    **The review unit is the tasks.md `##` group, not the single task:
    implementation is dispatched per task, but one group review (spec
    compliance + code quality, two sections of one report) runs once per
    group, at the group boundary. Do not reorder, skip, or merge.
    (REFACTOR-only groups run a reduced flow — see below.)**

    Commit behavior assumes the agent host has git permission. If commits
    cannot be made, the discipline degrades to in-memory steps; do not skip
    the test-first sequencing regardless.

    ─── Review findings: severity, pass rule, fix budget ───
    Every reviewer (group review, Final review) tags each finding with
    exactly one severity — `high` / `medium` / `low` — using the scale in
    execution-plan.md's "Review findings" section, and names the task
    number(s) it concerns. Paste that scale into every reviewer dispatch.
    - k = fix rounds already used for this group (0 at the first review);
      both sections of the group report share the same k.
    - PASS, first review (k = 0): zero findings of any severity in either
      section. Even a low-only list triggers fix round 1 — low findings
      get exactly one guaranteed fix attempt.
    - PASS, re-review (k ≥ 1): zero medium/high findings in either
      section. Leftover low findings are recorded (see "Recording deferred
      findings") and never trigger another fix round; if a fix round runs
      anyway for medium/high, hand them to the Implementer as optional
      items.
    - FAIL = anything else → one fix round, if budget remains.
    - Fix budget: 3 rounds per group, spec and quality findings together
      (Final review: 3 rounds total). One round = one fresh Implementer
      dispatched with the findings list from both sections (round 1: every
      finding; rounds 2-3: medium/high mandatory, low optional) and the
      affected tasks' context, then a re-review by a fresh Group Reviewer.
      Model per round: round 1 = Implementer default model; round 2 = one
      tier up; round 3 = strongest tier.
    - Re-review contract: the reviewer also receives the previous round's
      findings and must first mark each one resolved / unresolved before
      adding anything new. New findings are allowed but count against the
      same budget; nothing resets the counter.
    - Budget exhausted with medium/high findings remaining → do NOT
      dispatch a 4th fix. Record the remaining findings as deferred, treat
      the review as passed-with-deferred, and proceed exactly as if it had
      passed. This is the hard stop against reviewer / fix churn.
    - A reviewer that returns findings without severity tags, or without
      the two-section layout, is redispatched once to fix the report (this
      does not consume a round).

    ─── Recording deferred findings ───
    Append to design.md under `## Deferred Findings` (create the section at
    the end of the file if absent), one line per finding:
    `- [<severity>] §<group> / <section> / round <k>: <finding> (task X.Y)`
    `<section>` is `spec` or `quality` for a group review, `final` for the
    Final review (whose group is `all`); k is the round of the review that
    ended the loop (leftover low findings at a passing re-review use that
    re-review's k). This list is handed to the Final Code Reviewer (Step 9)
    and reported to the user at the end of apply (Step 11).

    ─── Per Group: coherence pre-flight ───
    1. Identify the current group: the next `##` section in tasks.md with
       unchecked boxes. Confirm it ends in a spec-coherent state: the
       group's tasks combined leave no dangling intermediate state (e.g.,
       a helper nothing inside the group consumes). If the coherent point
       lies in a later group, stop and fix the grouping in tasks.md (a
       planning fix, not a code fix) before dispatching anything. A group
       should stay within 3 RED/GREEN pairs.
    2. Note the current commit hash as the group's review base; the group
       diff reviewed in Steps 6-8 is everything committed after it.

    ─── Per Task (inside the group): dispatch Implementer ───
    3. Read execution-plan.md for the Implementer's default_model and upgrade triggers.
    4. Dispatch a fresh subagent as Implementer with:
       - The complete text of the task from tasks.md (the RED + GREEN pair)
       - The matching entry from test-plan.md (test name / scenario / assertion / why first)
       - The relevant spec.md section (only the capability this task touches)
       - The relevant design.md section (decisions and constraints affecting this task)
       - If the task produces an intermediate state (something only a later
         task in this group consumes), one line naming that consumer task
         and how it will consume it (so the interface lines up)
       - Explicit instruction: write the RED test → run tests, see it fail
         → write minimum GREEN implementation → run tests, see it pass
         → self-review → commit
    5. Implementer reports status:
       - DONE: dispatch the next task in the group; after the group's last
         task, proceed to Step 6 (group review).
       - DONE_WITH_CONCERNS: read concerns. If they are about correctness or scope,
         resolve before continuing. If they are observational (e.g., "this file grew
         big"), log and continue.
       - NEEDS_CONTEXT: supply the missing context; redispatch with the same model.
       - BLOCKED: follow escalation rules — context gap → add context;
         reasoning gap → upgrade model; task too big → split; plan wrong → escalate.
         Never redispatch the same model under the same conditions.
       Do not check off any box yet — boxes are checked only after the
       group review passes (or defers).

    ─── Per Group: review (spec compliance + code quality) ───
    6. When every task in the group reports DONE, dispatch a fresh subagent
       as Group Reviewer (model per execution-plan.md) over the group's
       combined diff (all commits since the review base). It receives the
       group's full task texts, the matching test-plan entries, the
       relevant spec / design sections, the severity scale, and (on a
       re-review) the previous round's findings.
       Required first action for the reviewer: restate the section headings of
       the spec / test-plan excerpts it received; if they do not match the group
       under review, report NEEDS_CONTEXT instead of reviewing (the orchestrator
       reassembles the context and redispatches).
    7. Sole task: one report with two sections, in this order, every
       finding tagged with severity and the task number(s) it concerns.
       - Section A — Spec compliance: answer "does the code match the
         spec?" Look at requirement coverage of the capability, scope
         creep, RED → Scenario mapping for each task, and whether every
         intermediate state inside the group got consumed by the group's
         end. Do NOT comment on naming, structure, or quality here.
       - Section B — Code quality: naming, duplication (including between
         this group's tasks), edge cases, error handling, readability,
         consistency with existing style. Do NOT re-litigate whether the
         spec is right here.
       Keep the sections separate; a finding belongs to exactly one.
    8. Apply the pass rule (k = fix rounds already used for this group):
       ✅ PASS (k = 0: no findings at all; k ≥ 1: no medium/high in either
          section) → record any leftover low findings (round k); check off
          every box in the group; proceed to the next group (back to Step 1).
       ❌ FAIL, k < 3 → one fresh Implementer (model for round k+1) fixes
          the findings of both sections (round 1: all of them; later
          rounds: medium/high, low optional) → back to Step 6 as a
          re-review.
       ⏭ FAIL, k = 3 → record the remaining medium/high findings as
          deferred (round 3); check off every box in the group; proceed to
          the next group. No 4th fix.

    ─── REFACTOR tasks ───
    Dispatch a fresh Implementer per REFACTOR task like any other task in
    its group, with this contract instead: refactor only, no behavior
    change, full test suite stays green, commit `refactor: <description>`.
    At the group boundary its commits are covered by Section B; Section A
    findings must not target them (no spec-visible behavior may change).
    For a group made up solely of REFACTOR tasks the reviewer fills
    Section B only and states "no spec-visible change" in Section A.

    ─── After all groups complete ───
    9. Dispatch a fresh subagent as Final Code Reviewer (model and checklist
       per execution-plan.md) over the full set of commits to confirm
       cross-group integration is consistent. It also receives the severity
       scale and the current `## Deferred Findings` list from design.md,
       and must give a verdict per deferred entry — stands / resolved /
       false positive. Verdicts are not Final findings and never trigger a
       fix round; they only annotate the list.
    10. Apply the pass rule (k = Final fix rounds already used):
        ✅ PASS (k = 0: no findings at all; k ≥ 1: no medium/high) → record
           any leftover low findings (group `all`, section `final`, round
           k); proceed to Step 11.
        ❌ FAIL, k < 3 → one fresh Implementer (model for round k+1) fixes
           the findings (round 1: all of them; later rounds: medium/high,
           low optional) → back to Step 9 as a re-review.
        ⏭ FAIL, k = 3 → record the remaining medium/high findings as
           deferred (group `all`, section `final`, round 3); proceed to
           Step 11.
        Then append the reviewer's verdict to each `## Deferred Findings`
        entry (`→ stands` / `→ resolved` / `→ false positive`).
    11. Report back to the user: groups completed, and the full
        `## Deferred Findings` list (or "none"). Any entry marked `high`
        and `→ stands` must be called out at the top of the report. Then
        apply is done.

    ─── Forbidden ───
    - Dispatching multiple Implementer subagents in parallel (they will conflict)
    - Reviewing mid-group "for safety" (mid-group states are legitimately
      intermediate; per-task review re-creates the false-positive churn the
      group boundary exists to remove)
    - Skipping the group review at a group boundary (REFACTOR-only groups
      still get Section B)
    - Splitting the group review back into two separate reviewer dispatches
      (one Group Reviewer, one report, two sections, one shared budget)
    - Letting Section A comment on naming/structure, or Section B re-litigate
      the spec (each section stays in its lane)
    - Checking off any box before its group review passes (or defers)
    - Moving to the next group with a medium/high finding that is neither
      fixed nor recorded under `## Deferred Findings` (fix or record —
      never neither)
    - Running a 4th fix round on any group or on the Final review (the
      budget is 3; defer instead)
    - Passing a first review (k = 0) that still lists any finding, low included
    - Failing a re-review (k ≥ 1), or dispatching a fix round after round 1,
      over low findings only
    - Accepting reviewer findings that carry no severity tag or no section
    - Letting the Implementer's self-review replace group review (both are required)
    - Waving through "close enough" spec deviations while fix budget remains
      (deferring after round 3 is a recorded decision, not a wave-through)
    - Redispatching a BLOCKED task with the same model under the same conditions
    - Letting any subagent read plan files directly (always paste the full task text)
    - Dispatching into a group that failed the coherence pre-flight
      (fix the grouping first)

    ─── When blocked ───
    - Stop. Record the blocker under `## Open Questions` in design.md.
    - Report back to the user.
    - Do not simplify tests or skip verification to make progress.
